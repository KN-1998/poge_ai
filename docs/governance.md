# 开源治理与许可策略

> 来源：原始提案“开源治理体系”与“公开蒸馏”部分，结合本项目实际采用 AGPL-3.0 后的落地说明。
> 这是项目治理意图的公开记录，不是法律意见；具体授权以 `LICENSE` 与 `NOTICE` 正文为准。

## 1. 为什么是 AGPL-3.0

原始设想要求“核心层强 Copyleft、禁止公共基础设施私有化、训练过程公开可审计”。在常见许可中，能满足“网络服务也必须回馈源码”的只有 AGPL-3.0（其第 13 条要求通过网络提供服务的修改版本向用户提供对应源码）。

GPL-3.0 不覆盖“只提供服务、不分发二进制”的场景，MIT/Apache-2.0 则允许闭源衍生，因此都不满足该要求。

采用 **AGPL-3.0-or-later**，意味着：

- 你可以自由使用、修改、分发本项目的代码；
- 若你修改后通过网络向他人提供服务，必须向这些用户提供修改后的对应源码；
- 不得对下游施加额外限制。

## 2. 三层治理规则

1. **核心层：强 Copyleft**
   核心代码、门控与路由实现、通信协议、训练脚本、训练日志、核心评测数据永久开源；衍生作品须同等开源。核心层不接受“仅在内部使用”的例外。
2. **生态层：允许商业化**
   垂直模型、行业工具、记忆库、托管服务、硬件适配可以正常收费。收费不违反本许可——AGPL 约束的是源码可得性，不是价格。
3. **中立共治**
   全流程公开可审计；任何人可提改进；重大路线由公开评审决定；不接受单一商业主体单方面改变方向。

## 3. 许可边界

| 对象 | 许可 | 说明 |
|---|---|---|
| 软件代码（`src/`、`tests/`、脚本） | AGPL-3.0-or-later | 见 `LICENSE` |
| 文档（`docs/`、`README.md` 等） | CC BY-SA 4.0 | 见 `NOTICE` |
| 第三方模型权重 / 数据集 / 论文 / 工具 | 各自原始许可 | 本仓库不为其重新授权 |
| 未来发布的模型权重 | 待定，须经 ADR | 需先解决“权重是否属于 AGPL 意义上的源码”问题 |

最后一行是**已知的未决问题**，不应被读作已承诺采用 AGPL。发布权重前必须单独讨论并记录决策。

## 4. 公开蒸馏与署名

- 任何利用其他模型输出进行训练的过程，必须记录教师身份、版本、调用时间与用途；
- 不允许无署名的灰色蒸馏；
- 教师与贡献者的署名随训练记录一并公开；
- 贡献者保留其贡献的著作权，提交即表示同意按本仓库对应许可发布；
- 如未来引入 CLA 或 DCO，须先公开讨论并记录 ADR。

## 5. 治理的已知张力

公开记录矛盾，而不是假装没有：

- **AGPL 与“鼓励公司采用”之间的摩擦**：强 Copyleft 会劝退部分商业集成方，这是主动选择。
- **“强制开源”与“中立共治”之间的张力**：谁来判断某次修改属于“核心层”？目前没有仲裁机构，只能靠公开讨论与时间戳留痕。
- **训练过程全公开与隐私、安全之间的冲突**：真实用户数据不能因为“公开审计”就进入公开日志。默认规则是：审计公开的是流程与来源，不是原始用户内容。
- **署名义务的可执行性**：技术上无法强制，只能靠社区规范与可追溯的记录设计提高违约成本。
